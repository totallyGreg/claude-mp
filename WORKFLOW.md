# Development Workflow

How changes to this marketplace are planned, versioned, validated, and released.

## Where things live

| What | Where | Notes |
|------|-------|-------|
| Work tracking | GitHub Issues | **Source of truth.** Task checklist in the issue body |
| Pre-work design | `docs/plans/YYYY-MM-DD-NNN-<topic>-plan.md` | Complex work only (multi-file, architectural, needs research). In the repo, not `~/.claude/plans/` |
| Post-work learnings | `docs/lessons/<topic>.md` | Cross-skill patterns worth keeping |
| Release notes + metrics | `plugins/<p>/README.md` | Mostly generated by skillsmith (see [Plugin README](#plugin-readme)) |
| Plugin metadata | `plugins/<p>/.claude-plugin/plugin.json` | Only home for `version`, `description`, `author` |
| Catalog | `.claude-plugin/marketplace.json` | Entries hold only `name`, `source`, `category` |

## One-time setup (per clone)

```bash
git config core.hooksPath .githooks
```

## Flow

1. **Issue.** `gh issue create --title "<plugin>: <change>" --label enhancement --body "..."` with a task checklist. For complex work, write the plan in `docs/plans/` first and link it from the issue.
2. **Branch.** `feature/<name>`, `bugfix/<name>`, or `experiment/<name>-<date>`. A trivial fix may go straight to main; the same checks apply.
3. **Bump versions in the first commit that touches a plugin or skill** (see [Versions](#versions)). Pick PATCH/MINOR/MAJOR now; raise it later on the branch if the scope grows.
4. **Implement.** Reference the issue in commit messages: `feat(<plugin>): <what> (#123)`. Stage files explicitly (never `git add .`).
5. **Validate skills before committing skill changes** (required by `.claude/CLAUDE.md`):
   ```bash
   uv run plugins/foundry/skills/skillsmith/scripts/evaluate_skill.py plugins/<p>/skills/<s> --quick --strict
   ```
   When changing agents, commands, or hooks, also run the matching plugin-dev skill (see [Component checks](#component-checks)).
6. **Record the release** in the plugin README. `/ss-improve` and `/as-improve` do this end to end; by hand:
   ```bash
   E=plugins/foundry/skills/skillsmith/scripts/evaluate_skill.py
   uv run $E plugins/<p>/skills/<s> --update-readme                          # Current Metrics + eval receipt
   uv run $E plugins/<p>/skills/<s> --export-table-row --version X.Y.Z --issue 123   # Version History row
   uv run $E plugins/<p> --update-components                                 # if components were added/removed
   uv run $E plugins/<p>/skills/<s> --verify                                 # score matches receipt + README
   ```
   Add a row to the plugin's `## Changelog` for the new plugin version. Never record a score you didn't get from a tool run.
7. **PR and merge.** `/mp-status` should report nothing pending.
8. **Close the issue** (see [Closing an issue](#closing-an-issue)).
9. **Optional: tag** with Anthropic's CLI after merge: `claude plugin tag plugins/<p> --push` creates `<p>--v<version>`. Tags only matter when other plugins declare version ranges on this one.

## Versions

Claude Code updates an installed plugin only when its `plugin.json` `version` changes. So, compared with the merge-base of HEAD and `origin/main`:

| Changed | Must be raised |
|---------|----------------|
| Any file under `plugins/<p>/` | `plugins/<p>/.claude-plugin/plugin.json` `version` |
| Any file under `plugins/<p>/skills/<s>/` | also `plugins/<p>/skills/<s>/SKILL.md` `metadata.version` |

- New plugins and skills pass if they declare a version. Removed skills need only the plugin bump.
- Multi-skill plugins (foundry, terminal-guru, …): the plugin version is its own release number, raised by at least the level of the largest component change. Single-skill plugins usually keep both versions equal.
- Merging main into a branch moves the base forward, so two branches that bumped the same plugin get a fresh bump instead of colliding silently.
- A changed plugin's `description` must be 200 characters or fewer: it's the `/plugin` listing text (what it does, not how). Skill and agent descriptions are what drive triggering; skillsmith and agentsmith score those.
- Never put `version` in `marketplace.json` (Anthropic: "Don't set `version` in both `plugin.json` and the marketplace entry").

**Pre-commit hook** (`.githooks/pre-commit`) runs `validate.py --staged`, which blocks the commit on:
- a missing bump or an over-long description (rules above),
- `version` in a marketplace entry,
- errors from Anthropic's `claude plugin validate` (strict for the marketplace; errors only for changed plugins).

It never edits or stages files. Preview any time with `/mp-status`. Bypass in an emergency with `git commit --no-verify`.

## Plugin README

`plugins/<p>/README.md`, mostly maintained by skillsmith:

- `What's inside` / `Install` / `Components`: autogen blocks from `--update-components` (hand edits inside the fences are overwritten)
- `## Changelog`: one row per plugin version (hand-written)
- `## Skill: <s>` → `### Current Metrics` (from `--update-readme`) and `### Version History` (rows from `--export-table-row`; MINOR-only, so PATCH releases fold into their MINOR row)

## Component checks

| Changed | Check with |
|---|---|
| `agents/*.md` | `plugin-dev:agent-development`, then `/as-evaluate` |
| `commands/*.md` | `plugin-dev:command-development` (frontmatter with `description`, `argument-hint`) |
| `hooks/hooks.json` | `plugin-dev:hook-development` (quote `"${CLAUDE_PLUGIN_ROOT}"`) |
| Any of the above | `claude plugin validate plugins/<p> --strict` |
| `SKILL.md` | `plugin-dev:skill-reviewer` and skillsmith `--explain` |

## Closing an issue

1. Every checkbox in the issue body is checked (`gh issue edit N --body-file ...`).
2. Follow-up work has its own issues.
3. Close with a summary comment: status, results/metrics from tool output, commits, follow-ups:
   ```bash
   gh issue close N --comment "Complete: <summary>. Commits: <shas>. Follow-ups: #M"
   ```
   Don't rely on `Closes #N` in a commit alone; it closes without the summary.
